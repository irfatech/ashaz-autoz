# Implementation Plan: Faster, Shorter Vehicle Form

Spec: [SPEC-vehicle-form.md](../SPEC-vehicle-form.md) (approved). Tasks: [todo-vehicle-form.md](todo-vehicle-form.md).
This is separate from `tasks/plan.md`, which still has unfinished Phase 4 work and is left untouched.

## Overview

Make adding and updating a car mostly taps instead of typing, fix the inconsistent data that typing
caused, and make a freshly saved car appear at the top of the list. Only the CMS input widgets change;
stored field names and shapes stay the same, so the site, `/app`, the sitemap and the checks keep working.

## Architecture decisions

- **A guard first.** Before any list exists, add a check that every value already stored in a car's file is
  a valid choice in that field's CMS pick-list. It starts passing trivially (no lists yet) and then
  protects each conversion: a list can never be shipped while a car still uses a value it does not offer.
- **The pick-lists live only in `config.yml`.** No second copy in TypeScript. The guard reads the YAML.
- **The year list is generated at build time**, because manual CMS initialization cannot edit an existing
  field's options. A small build step rewrites the year options in the *deployed* `admin/config.yml`;
  the source file keeps a static list for local development. The schema's maximum year uses the same
  rule ("next year"), so the list and the schema always agree.
- **"Recently added" is a hidden field** with `default: "{{datetime}}"` (verified in the real CMS: set on
  create, regenerated by Duplicate, untouched by edits). Existing cars are given their real date from
  git history *before* the field goes live, because a car without one is stamped "now" on its first save.
- **Data changes are one-off scripts with a dry run**, a before/after table shown to you, and an explicit
  OK before they run. Each is its own commit so it can be reverted alone.

## Dependency graph

```
V1 guard check ─────────────────────────────────────────────┐
V2 recently added (CMS+schema+sort) ─► V2b backfill ─► Checkpoint A (owner sees it)
V3 year list (generator + schema max)                       │
V4 compact pass (radios, remove fields, reorder, hints) ─► Checkpoint B (measure)
V5 colors list ─► V6 engine list ─► V7 features list ─► V8 brand list ─► Checkpoint C
V9 monthly rebuild (deploy.yml)
V10 final measurement + report
```

V5–V8 all edit `config.yml`, so they run in sequence, not in parallel. V1 comes first so each of them is
protected. V2 comes before the compact pass because it is the problem you hit today.

## Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| A multi-select drops stored values that are not in its list | High (data loss) | V1 guard fails first; V7 starts with a real-CMS test of an unknown stored value; every value is mapped before the list ships |
| An old car without "added on" is stamped "now" on first save | High (wrong sort) | V2b backfills all cars from git history before release; verified behavior in the real CMS |
| The year list generator rewrites the wrong text or fails silently | Med | Pure function with unit tests; the build fails if the markers are missing; a check confirms the output list |
| A select saves numbers as text (`"2021"`) | Med | V3 and V4 verify in the real CMS that `year`, `doors`, `seats` are saved as numbers; the schema already coerces |
| A brand or engine not in a list blocks the owner | Med | Engine, features and colors are optional or have wide lists; brand list has ~40 entries; adding one is a one-line change |
| Radios wrap on a narrow phone | Low | Checked at 375 px in the real CMS before finishing V4 |
| `commit_date` ("last updated") sort cannot be verified without the live GitHub connection | Low | Added as a bonus option only; the primary "Recently added" sort does not depend on it |
| A stale CMS browser tab writes old fields (`currency`, `bodyType`) | Low | Those keys stay valid in the schema; nothing is removed from it |
